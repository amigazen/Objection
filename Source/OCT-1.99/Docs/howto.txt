   1.1. System Components         1.1. System Components

        A running OCT application is the product of source files,
   interface definitions, and translation programs.  The Object C
   Translator programs include an OCT to "C" source code
   translator, a class interface helper, and a pre-linker utility.
   Your site must provide a K&R version 1 [Kern78] "C" compiler.  

        The interface definition file includes information about
   the class, its superclass, and method return types.  The
   prelinker program arranges for the needed classes to be included
   from the OCT object library.  The output "C" file is then linked
   along with application files and the OCT libraries.

   Now that you got the thing, it's time to use the thing.  The
   thing, here, refers to the Object C Translator system:
   translator, utilities, and class libraries.  At present (April
   1990), the system is remarkably independent of the actual
   machine it's running on.  Applications can be generated with
   16-bit or 32-bit int's.  The translator relies strictly on the
   "C" runtime library, not any Amiga or U*NX specific routines.
   So developing an application should be just like developing any
   other "C" language application.  Well, it's almost the same...  

        A few rules for generating an application will be detailed
   below.  These refer to source and ____ rules.  In most                                     make
   circumstances, plain "C" files may be added coagulated into your
   application.  These files, however, won't be taking advantage of
   any special object oriented features.  By adding one translator
   directive (@includes), a source file may onw open up the power
   of this exciting programming system.  The system also requires
   additional libraries at link time.

   In the object oriented world, the programmer dreams of objects
   that actions affect.  Objects are usually modeled after real
   life entities.  "Look for structure, other systems, devices,
   things remembered, roles played, locations, organization units,
   and descriptive catalogs." [Coad89] "As a system evolves, its
   tasks may change drastically.  Much more persistency may be
   found in the classes of data it manipulates.." [Meyer88] These
   objects may maintain state internally, or relie on other objects
   to remember.  

        Objects are instances of a class, and all objects of a
   given class react similarily (although, based on state,
   reactions may be different).  Each class will be a problem
   solving module.  "Modular concepts apply to programming as well
   as specification and design." [Meyer88].

   5.2. After Translation         5.2. After Translation

        A prelinker is used to build a list of classes that will be
   brought together to form the final application.  A small .c file                                                            .c
   is built, which must be compiled and added into the list of
   object modules for the appliction.  This list tells the linker
   which classes to extract from the library, including any
   dependencies the included classes need, like other classes.
   It's also used by the substrate at startup-time to build a
   central list of method selector codes and class names.
   Normally, this small file need only be rebuilt when the list of
   modules the user provides changes in some way, or a new class is
   added to the application.

   7.1. Factories          7.1. Factories

        Software factories create software objects.  These objects
   carry inbedded information about how much space they occupy and
   what kind of method selectors they respond to.  In a factory
   method, "self" refers to the factory object.  It is a real
   variable (along with "_cmd" which is the method selector)
   declared as part of the method definition clause.  "self" can be
   reassigned to a new instance of itself and returned from a
   factory method, just as in [Cox86].  However, this practice is
   discouraged by the author.  Factory objects can never be
   free'd.  


   7.2. Instances          7.2. Instances

        Once created ([new] method), objects can be manipulated and
   assigned at will.  The caller must track memory usage since
   there is no automatic garbage collection nor referencing
   counting.  This does place an extra burden on the programmer,
   but all of us learned Pascal in order to better discipline
   ourselves...

   _______ __________________________________    _______ __________________________________   Section 8. Interpreting Runtime Errors   Section 8. Interpreting Runtime Errors

   Because of the dynamic nature of messages and objects, only a
   limitied amount of checking can be done at compile time.  If
   this system, all checking of whether a message is appropriate
   for the object is done at runtime.  If something is amiss, the
   application can abort.  

        When the first thing your program does is give the "message
   selector 0" error, suspect your makefile.  If the prelinker                                   makefile.
   isn't told about your main.m then its method won't be resolved                         main.m
   (they'll remian 0).  The program will start up, but abort with
   the first message performed from your main file.  

        If you send a message to a nil ptr, the message dispatcher
   will just ignore your attempt.  If the object has been free'd,
   but you have a dangling pointer, you'll also be ignore.  There
   are compile time switches that can provide some diagnostic
   messages in these instances, but usually they are a nuicence to
   have around.  

        If you send a message that an object can handle, you'll get
   an error message like: 


       (oc_error) Slider does not recognize [moreGadgets:]!

       This means an object of the class Slider could not handle                                         Slider
   the method "moreGadgets:", and neither could any of its parent
   classes.  If the class name had been Slider then a factory                                        Slider
   method was being invoked.

   10.1. Extracting Instance Variables        10.1. Extracting Instance Variables

        Although objects are supposed to be complete and
   inaccessible from outside the methods code, you can access the
   variables if you really need to.  From inside a class you can
   reference any superclasses' instance variables using "self->" in
   front of the reference.  



       - (int) capacity
       {
           /* reach into another class and read its mind! */
           struct { @defs(IdArray) }   *id_ptr;

           id_ptr = (void *) self->contents;    /* Grab pointer to array obj */
           printf( "its capacity=%d\n", id_ptr->capacity );

           return( [id_ptr capacity] );
       }
