   Object oriented programming is now coming into acceptance in
   major computing circles.  Software houses such as Microsoft and
   Borland International are finally offering object oriented
   Pascal, years after Apple first made available Niklaus Wirth's
   Objective-Pascal for the Macintosh system.  AT&T now offers an
   object oriented version of "C" called C++ [Stro86].  The NeXT
   computer has been designed around Objective-C version 4.  Major
   companies are committing themselves to this new challange.  

        The computers of today are finally overcoming many of the
   "drawbacks" that have long putoff serious consideration of an
   object oriented system [Cox86].  Large memories, fast disks,
   graphic diplays, and capable processors are today reaching a
   financially feasible level to make the ideas of object oriented
   possible for the masses.  

        This programming language is an attempt at hybriding a
   medium level language with object oriented constructs.  The goal
   is to provide flexibility with classical (?) object oriented
   programming layout (ala Smalltalk).  The translator accepts the
   hybrid language and ensures its output is complete, legal "C"
   code.  The translator system is model after Objective-C as
   presented by Dr. Cox in [Cox86].  This author's particular
   system is currently in the public domain.  

        The alpha releases of OCT started in August 1989.  The
   first Amiga "release" was January 1990, along with the
   Xenix/386.  The planned rollout schedule is as follows.  An
   MS-DOS version should appear after the summer of 1990.  A second
   Amiga version should also appear about this time, and will be
   released to Fred Fish.

   2.1. Kind-of Object Oriented        2.1. Kind-of Object Oriented

        Following the lead in [Cox86], OCT is an object oriented
   preprocessor for the "C" language.  For the programmer, the
   system provides single inheritance.  The root class is named
   Object This class is mandatory for any OCT application; all   Object
   other classes are pulled in as required by your application.
   Allocated objects are of the single type "id", and any object
   reference may be assigned to any other object referring
   variable.  The future reveals that typed object references will
   be introduced, and will co-exist with untyped object
   references.  

        Method selectors are bound dynamically at run-time.  Any
   method may be sent to any object; successful understanding is
   another matter.  Methods are generally public unless you don't
   mention them in the public interface file.  Custom places an
   underscore () in front of private methods.  Instance variables
   are hidden from the application, but not completely unreachable
   by it.

   _______ ______________________________    _______ ______________________________   Section 3. What the Translator Does   Section 3. What the Translator Does

   The translator handles one class at a time.  The definition of a
   class is split between the public interface definition header
   file and the private class implementation code file.  (The
   totality of methods a class responds to includes those of its
   superclasses, also.) The public interface defines the class's
   instance variables and methods that it specifically implements.
   (See also C++ in [Stro86].) The implementation file holds source
   code to implement the methods, and it can include any private
   methods to assist the class's objects in carrying out their
   work.  

        Before compiling any class, information about the class's
   single superclass must be available.  This superclass is used to
   link the class into the class heirarchy.  Instance variables are
   collected by reading in the interface definition file for all
   the superclasses.  

        A implementation difficulty for object oriented systems is
   translating the method selectors into a "universally unique
   code" for the particular collection of classes that are needed
   to form the application.  The method choosen by Cox [Cox86] is
   for each phylum (grouping of classes) to maintain an array of
   codes representing the method selectors unique to that phylum,
   ie, those not defined in its super-phylums.  (Phylum is a
   collection of related classes, such as Foundation, Collection,
   or Windowing.) Values from this array are read out and passed as
   the message selector code.  At startup-time, each phylum's array
   is adjusted by a scalar representing the count of methods
   already defined and adjusted in the phylum before it.  This has
   the advantage that each phylum can be built and compiled
   separatedly and without knowledge of other phylums.  The cost is
   small at startup-time, and a single indirection during message
   invocation (array fetch at a fixed offset).  

        Once the program is ready to be linked, Cox's runtime
   substrate constructs a single list of classes.  This list is
   used to preset all classes initially at startup-time, ie,
   [Sequence initialize].  A single list of method selector names
   is also constructed..  This list is used primarily for run-time
   error reporting (ie, "error: 'ByteArray' doesn't respond to
   [display:rop:]").  These lists are built by the _______ ,                                                   prelink
   compiled, and passed to the system's linker along with the other
   module names.  

        For OCT, the basics of the above system have been

        The message expression is the primary reason the translator
   was built.  Messages begin with a left square bracket ([) and
   close with a right square bracket (]).  Between the square
   brackets is the message target, and some combination of
   selectors and arguments expressions, seperated by spaces (except
   va-dcl, see below).  The smallest message expression is a target
   and method selector like "new" or "hash".  The method may also
   take arguments, which are separated from the selector by a colon
   (:), ie "at: 1" and "put: target".  This syntax is similar to a
   "code block" in Smalltalk.  

        Some messages allow a variable number of arguments to
   follow the fixed selectors.  These arguments are unlabeled and
   are separated by commas (,).  The translator will automatically
   append "vaDcl:" to the method name internally, thus the last
   statement below invokes the message "with:vaDcl:".  If a method
   name is unknown, another search with "vaDcl:" appended is
   tried.  This way, "vaDcl:" methods may take a single parameter
   (after the opening name) and not require a trailing dummy
   parameter (see last statement in sample below).  This is called
   auto-detection of "vaDcl:" type methods.

   Translation is accomplished in four phases.  Source starts as .m                                                                 .m
   files (methods), are translated to .c files, and then compiled                                      .c
   to object files.  The system linker, using the prelinker's
   output, coagulates the user and system classes creating the
   user's application.  

        The first two passes are driven by OCT, which calls ___                                                            cpp
   first.  The translator then converts class definitions and
   methods into legal "C" code.  The translator uses information in
   the @interface clauses to relate the external classes.  The
   system's "C" compiler runs next.  The prelinker creates a list
   of classes for use by the substrate.  Finally the system's
   linker/loader pulls together object and library modules.  

        The OCT translator first uses ___ to process the input                                      cpp
   source file, stripping comments, inserting included files, and
   choosing conditional code.  If the source code depends on the
   "C" compiler defining certain symbols relating to specific
   options, like _LARGE_DATA_MODEL, then these define's must be                 _LARGE_DATA_MODEL,
   given explicitly to ___ to pass to ___ (see "Translator                       oct            cpp
   Gotchas!" below).  The processed text is stored into a temporary

   dictionary describing the methods is built, and the file is

   4.1. Translator Gotchas!         4.1. Translator Gotchas!

        Discussed here are a few points to keep in mind when using
   the Object C Translator.  The warnings here are mostly the
   result of certain assumptions to simplify the translator a bit,
   and will probably change as the translator evolves.  These

   idiosyncracies will probably return errors from the "C" compiler
   instead of compiling incorrect code.  But if your application is
   amiss, you should first suspect the generated code.  

        The first idiosyncracy concerns the use of ___ to first                                                   cpp
   treat the code.  Since it doesn't know about "//" comments, the
   comment text has to obey certain rules; rules like matching
   quote marks.  So for a line like: "// don't look now!", ___ will                                                           cpp
   complain about "unterminated string" on the line _____ the "//"                                                    after
   comment.  What happens is ___ is tripping over a single quote                             cpp
   (') in the comment line.  There is no matching single quote on
   the line.  If the error line is a comment, or just after a
   comment line, just ignore this error message.  Also, since your
   host compiler didn't invoke ___ , there is no way symbols                               cpp
   relating to the program's memory model can be set.  These
   defines can passed using the -p or -d options of OCT, or more
   permanetly set using environment variables.  

        Among high-level programming languages, monadic operators
   that trail the expression are rare, except in "C" [Kern78].  The
   usual handling cares should be applied to auto-increment and
   auto-decrement operators.  Witness the famous: "a++ + ++b."
   Inserting a few parenthesis here will only make the code more
   understandable.  If you forget the parenthesis, the post-inc and
   post-dec will associate right to left, in accordance with K&R
   [Kern78].  This code sample points out a few concerns.  


       - foo
       {
          id   *there, cls = [super class];

          there = (id *) IV(self);
          while( *there )
             [(*there++) free];

          if( [self hash] > 5 )
             cls = [self class];
          (there-1)[1] = nil;         /* array store */
       }  /* - foo */


   Because the translator simply inspects the tokens as they
   appear, and not really following what they mean, it can get
   confused at times.  How one token relates to its neighbors isn't
   inherit in the parsing.  

        The above line marked "array store" is an example of where
   a closing parenthesis ()) would be next to an open square
   bracket ([).  The translator assumes this really is an array
   store (since the syntax is legal and correct).  rather than
   going for the message expression.  Note, if a function call were

   added to the beginning of the line, (ie, "foo(there)[1] = nil;")
   the square bracket ([) might be mistaken as beginning a

   6.1. Factories          6.1. Factories

        Software factories create software objects.  These objects
   carry pointers to structures that contain information about how
   much space the object occupies and which methods it responds
   to.  In a factory method, "self" refers to the factory object.
   It is a actual parameter (along with "_cmd" which is the method
   selector) declared as part of the function definition.  "self"
   can be reassigned to a new instance of itself and returned from
   a factory method, just as in [Cox86].  However, this practice is
   discouraged by the author.  Factory objects can never be
   free'd.  


   6.2. Instances          6.2. Instances

        Once created ([new] method), objects can be manipulated and
   assigned at will.  The caller must track memory usage since
   there is no automatic garbage collection nor referencing
   counting.  This does place an extra burden on the programmer,
   but all of us learned Pascal in order to better discipline
   ourselves...  

        There is a facility to provide cleanup processing for
   classes.  At any time, a method may declare an "at exit"
   handler.  A function that takes no parameters and returns no
   specific value will be called when the application is finished,

       }  /* _msg */

   The dispatcher, _msg(), uses the relations of figure 6-1 to find
   a dictionary of method selector codes and function (method)
   pointers (`IMP' pointer).  It does this by first moving to
   "self->isa", which always yields a "struct _SHARED" pointer.
   Inside the shared class structure is a pointer to the


   Barney - OCT                 pg. 23                   29-Jul-1993


   Object C Translator                                     Release 2


   selector-function dictionary.  A sequential search looks for a
   matching selector.  Each category of the class is searched.  If
   no match selector is found, then the object's superclass is
   consulted by moving to "class->clsSuper", and continuing the
   search.  The pseudo-code outlined in figure 6-4 describes the
   basic functions.  

        Some performance and portabilities decisions have been
   applied to the actual dispatcher (although it's still written in
   "C"..).  A cache of recently invoked methods helps speed the
   dictionary lookup.  The cache is indexed by hashing together
   "class" and "_cmd".  Which means that different load addresses
   will yield different hash values.  And allocating objects in
   varying sequences will affect how long an entry survives in the
   cache.  

        In order to allow the dispatcher to be written entirely in
   "C", arguments are copied from the caller's stack frame to the
   receiver method's stack frame.  Ideally, you'd want the
   dispatcher to be transparent and "jump through" into the
   receiver's method code.  In an actual implementation, the "jump
   through" code should be implemented in assembly since the
   application will gain the most from optimizing the inner loop.

   7.2. Future: Preprocessor         7.2. Future: Preprocessor

        Another directive is "@alias()" which assigns a method
   selector to call a another method.  This aliasing is private to
   the class definition, as each method selector will have its own
   unique selector code.  Aliasing can be used in some
   circumstances to save a little memory.  The protocol defined in
   an abstract class may default one method to behave similar to
   another method, where subclass are free to re-define either
   method.  The abstract class would alias the second method to the
   first method.  Also, methods with multiple trailing arguments
   can be quickly produced, ie "perform:", "perform:with:" and
   "perform:with:with:".  Here the method with most arguments would
   be defined, and the rest would simply alias to that method.  In
   order for the processor to not crash when handling alias'ed
   methods, the stack layout must be very lax.  Contrast this to
   machines that force static link frames, like the Prime 50 series
   and IBM 370 architectures.

   7.3. Future: Universal Name Binding       7.3. Future: Universal Name Binding

        A goal of the Object C Translator system is to eventually
   have the classes partitioned into system provided and user
   provided.  The operating system could then be a collection of
   resident classes the user's application links with, including
   some of their own classes, replacing any system classes
   seamlessly, as appropriate.  All programs would share a common
   pool for method selectors.  Interprocess communication would be
   very straightforward since a method invocation could just be
   packaged like an RPC (Remote Process Call) call.  Right now
   there is no way to know exactly how many parameters (or their
   byte widths) have been pushed on the stack.
